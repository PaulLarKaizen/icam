# ICAM Google authentication — GCO-style flow with Supabase sessions

## Decision

ICAM reuses the existing GCO web application's Google authorization-code route pattern:

- `GET /api/auth/google` creates an OAuth `state` and `nonce`, then redirects to Google.
- `GET /api/auth/google/callback` exchanges the authorization code server-side and validates the Google ID token.
- The callback establishes the application session through Supabase Auth, not a second ICAM-specific signed cookie.
- `GET /api/auth/session` exposes the verified user, active profile, and explicit roles; `POST /api/auth/logout` ends the Supabase session.

This adapts the GCO flow to the approved ICAM Supabase architecture. It deliberately does not copy GCO's custom HMAC session cookie or its email-domain-only authorization check.

## Google identity verification

The callback verifies the Google ID token signature against Google's rotating public JWKs and checks:

- issuer is `accounts.google.com` or `https://accounts.google.com`;
- `aud` (and `azp`, when present) matches the configured ICAM Google OAuth client ID;
- token is not expired and has a valid issued-at time;
- `nonce` matches the hash of the nonce generated by ICAM for this OAuth request;
- `email_verified` is true;
- signed hosted-domain claim `hd` is exactly `sdca.edu.ph`;
- a Google `sub` subject is present.

The `hd=sdca.edu.ph` authorization-request parameter is only a Google account-picker hint. It is not authorization proof. Email suffix alone is not accepted as proof of institutional membership.

After verification, the callback signs into the configured Supabase Google provider using `signInWithIdToken()`. It then records the verified `hd`, Google `sub`, and verification timestamp in Supabase `app_metadata` using the server-only Supabase secret key, and refreshes the user's Supabase session. These server-written claims are not stored in user-editable `user_metadata`.

The additional migration `20261120104439_require_verified_sdca_identity_for_rls.sql` requires the trusted `app_metadata` identity marker for the existing active-user and permission RLS helper functions. Thus the verified-domain requirement is enforced both in Nitro and in PostgreSQL RLS.

## Required environment configuration

Copy `.env.example` to `.env` and fill these values locally. Do not commit `.env` or paste secrets into issues or chat.

```dotenv
NUXT_PUBLIC_SITE_URL=http://localhost:3000
NUXT_PUBLIC_SUPABASE_URL=https://<project-ref>.supabase.co
NUXT_PUBLIC_SUPABASE_KEY=<publishable-key>
NUXT_SUPABASE_SECRET_KEY=<server-only-supabase-secret-key>
NUXT_GOOGLE_CLIENT_ID=<google-web-oauth-client-id>
NUXT_GOOGLE_CLIENT_SECRET=<google-web-oauth-client-secret>
NUXT_GOOGLE_REDIRECT_URI=http://localhost:3000/api/auth/google/callback
NUXT_AUTH_STATE_SECRET=<random-secret-at-least-32-characters>
```

`NUXT_SUPABASE_SECRET_KEY`, `NUXT_GOOGLE_CLIENT_SECRET`, and `NUXT_AUTH_STATE_SECRET` are server-only. They must never be prefixed with `NUXT_PUBLIC_`, included in browser bundles, or committed to Git. The callback URL must exactly match the configured ICAM site URL plus `/api/auth/google/callback`.

## Provider setup

1. Use an existing GCO Google OAuth web client only when the project owner authorizes ICAM's use and adds the ICAM callback URL to its authorized redirect URIs. Otherwise use a development OAuth client controlled by the project team and restrict its test audience appropriately.
2. Configure the same Google client ID and secret in the ICAM-DEV Supabase project's Google Auth provider. `signInWithIdToken()` requires the Google provider to be enabled and configured with the client that issued the ID token.
3. Add the local callback URI for development and the exact deployed callback URI when the deployment host is known.
4. Institutional production use remains subject to the approved SDCA Google OAuth credentials, IT approval, and applicable data-protection clearance.

No credentials are embedded in the repository. The code can be built and unit-tested without real OAuth credentials, but an end-to-end Google sign-in test requires the environment and Supabase provider settings above.

## Account activation and roles

The existing Auth trigger creates an `icam_profiles` row with `account_status = 'pending'`. Sign-in does not activate the profile and assigns no roles. The ICAM Application Administrator separately activates the account and assigns one or more explicit entries in `icam_user_roles`. Coordinator and Custodian must be assigned separately when one person performs both duties. Application Administrator and Designated Technical Administrator remain separate.

`requireIcamUser()` is called explicitly by protected Nitro handlers. It validates the Supabase session with `auth.getUser()`, checks the server-written verified identity metadata, requires an active ICAM orrofile, and loads current non-revoked role assignments. `requireIcamPermission()` then checks the requested permission against `icam_role_permissions`. No authorization decision relies on client-only route visibility or a single role field.

## Test command and limits

Run `npm run test:auth` for the Node.js built-in unit suite covering signed Google token checks, hosted-domain/audience/nonce failures, OAuth state integrity/expiry, trusted identity metadata, and single-multi-role permission mapping. The test suite uses generated local RSA keys and does not contact Google.

Live OAuth, active-account provisioning, per-user RLS, and endpoint integration still require an authorized Google client, a configured Supabase Google provider, and controlled test accounts. They must not be reported as end-to-end verified until those tests are run.
